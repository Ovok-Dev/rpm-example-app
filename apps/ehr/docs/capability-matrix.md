# Ovok capability and integration matrix

This matrix separates verified SDK/platform behavior from implemented app behavior. It was checked against installed `@ovok/core` declarations, existing mobile/dashboard code, and official Ovok documentation on 2026-10-08. The public sandbox capability statement describes the API surface; it does not grant this tenant permission to perform an operation.

| Workflow | Verified Ovok capability | Demo behavior | Sandbox behavior and boundary |
| --- | --- | --- | --- |
| Authentication | `OvokClient` uses Ovok authentication. The mobile app signs in patient accounts; the dashboard uses practitioner sign-in. | No account required. | Use a real patient or practitioner account in `public-example` or another configured sandbox tenant. No secrets in app bundles. |
| Patient identity | FHIR R4 `Patient` search/read/create is advertised; `invitePatient` is typed in `@ovok/core`. | The preloaded EHR/dashboard fixture and mobile demo share stable `demo-*` IDs. Mobile demo readings use the fixed shared fixture `demo-2048`. A patient newly registered in EHR demo state remains local to that EHR session and is not selectable in the mobile demo. | EHR searches by email to reduce common duplicate creation, creates a Patient, then requests an invitation. These are separate non-atomic writes. The invitation response does not prove delivery or acceptance. A deep link re-reads the requested patient with the signed-in account. |
| Intake and history | Patient, RelatedPerson, Condition, AllergyIntolerance, MedicationStatement, Consent, Questionnaire, and QuestionnaireResponse interactions are advertised. | Synthetic intake and checkbox status are local session state. | EHR creates Patient with supplied demographics/contact only. It reads Consent status and patient-scoped Observation/QuestionnaireResponse records. Legal consent capture, signed artifact, full intake questionnaire, conditions, allergies, medications, and RelatedPerson persistence are not implemented. |
| Practitioner and care team | Practitioner, PractitionerRole, CareTeam, and Task are advertised. | Synthetic clinicians and care-team assignment drive the enrollment workbench. | EHR searches accessible Practitioners and creates/updates a CareTeam. It does not persist reassignment history or assign a nurse unless selected. Assignment never expands backend access. |
| RPM enrollment | CarePlan, Goal, ServiceRequest, and Task are advertised by the public capability statement. | CHF program stages and questionnaire/template choices are synthetic. | EHR can create an active CHF CarePlan. It does not currently create a Goal, ServiceRequest, Task, questionnaire assignment, or monitoring schedule resource. The project policy still controls every request. |
| Device assignment | Device and DeviceUseStatement are advertised. Native SDK device catalog includes Viatom BP2 and Viatom F4/LeScale-family declarations. | BP2 + F4/LeScale-family kit inventory is a synthetic fixture. | EHR can link an actual accessible Device with DeviceUseStatement. The UI does not validate physical availability or confirm a BP2 + scale kit. Inventory, compatibility, shipping, delivery, returns, and replacement are not Ovok capabilities verified here. Confirm exact LeScale model/IFU. |
| Measurements | Mobile uses `OvokClient.saveMeasurement`; dashboard uses patient measurement-history SDK methods. | The EHR dev-only in-memory relay validates and shares synthetic mobile readings with EHR/dashboard. The two web apps poll every five seconds; this is not realtime. | Mobile sandbox writes remain patient-scoped. Dashboard reads authorized FHIR patient measurements. EHR displays authorized Observation records and source/reference/time when returned. API failures do not load demo data. |
| Signals | Read-only settings and `listSignalsRawAlerts` exist in the SDK. | Demo mode explicitly says settings and alerts are not simulated. | EHR and dashboard read project settings/open alerts only. No write, acknowledgement, inferred risk score, or diagnosis. Permission failures stay visible. Signals is a separate component. |
| Human messaging | FHIR Communication is advertised by the capability statement. Ovok WebSocket subscriptions can deliver criteria-based notifications when enabled. | Message-like fixture counts appear in sample data; there is no messaging UI. | EHR, dashboard, and mobile human messaging are not implemented. The platform capability is not a dedicated chat contract, receipt, or authorization grant. Any future UI must verify policy, subscription connection, patient/team recipients, and project feature. No typing, receipt, or notification behavior is claimed. AI chat is not human-to-human messaging. |
| Analytics and operations counts | FHIR reads/search are available; no verified aggregate analytics endpoint was found. | Counts derive from local synthetic fixtures. | Derive from accessible, paginated records. Label partial results and permission failures; do not present fabricated backend analytics. |

## Verified setup requirements

- Start from [Ovok's current documentation](https://docs.ovok.com/llms.txt). Check [project setup](https://docs.ovok.com/authentication/project-setup), [AccessPolicies](https://docs.ovok.com/access-policies), [FHIR R4](https://docs.ovok.com/api/fhir/r4), [Invitations](https://docs.ovok.com/invitations/invite-a-patient), [WebSocket subscriptions](https://docs.ovok.com/settings-and-features/features/websocket-subscriptions), [Signals](https://docs.ovok.com/signals), and the [Native SDK device catalog and IFUs](https://docs.ovok.com/native-sdk/guide/supported-devices) before adapting this example to a real project.
- A tenant code such as `public-example` identifies a project; it is not a credential, invitation, or access grant.
- Use the capability statement and the actual logged-in account's policy responses together. The capability statement does not prove project-specific authorization.
- Ovok AccessPolicies can be broad when policies are missing; administrators must configure least-privilege patient and practitioner access before testing real records.
- Invitation email templates, patient sharing settings, the invitation feature, patient app URL, and appropriate AccessPolicies are administrator prerequisites.
- The `websocket-subscriptions` project feature must be enabled for genuine live updates. Without it, offer manual refresh and state that the connection is not live.

## Implemented vertical slice and gaps

- EHR registration, invite request, accessible patient paging, chart record reads, Practitioner assignment, CHF CarePlan, and DeviceUseStatement creation are implemented through `@ovok/core`. AccessPolicy enforcement remains server-side.
- Demo workflow stages are local browser state. They are not persisted. The shared measurement relay is development-only and accepts allowlisted synthetic IDs and readings only.
- EHR Signals settings and alerts are read-only. EHR chart operations include Consent status display but do not create Consent resources or capture signatures.
- Dashboard and EHR patient links carry only a validated opaque ID; each app uses its own authenticated SDK client before showing sandbox records. The connected synthetic mobile readings cover only the preloaded `demo-2048` fixture, not newly registered EHR demo patients.

- **Physical kit logistics:** no verified Ovok inventory/shipping API or suitable complete resource model. Keep these statuses in demo state; sandbox mode can demonstrate device assignment only through Device and DeviceUseStatement.
- **Patient account linking:** invitations are asynchronous and privacy-preserving. A pending invite is not proof of email delivery, account existence, or accepted sharing. Refresh authorized patient search after acceptance.
- **Consent and complete intake:** the sandbox registration form creates demographics and an optional invitation only. It does not capture a signature or persist conditions, allergies, medications, or a validated questionnaire.
- **Human chat:** no app UI is implemented. Standard Communication CRUD and subscriptions may support a future message thread if the project grants access. There is no verified dedicated chat, read/typing/delivery receipt, or notification protocol.
- **Real-time state:** show live only after both feature support and successful WebSocket connection. Polling/manual refresh is not real-time.
- **Cross-application navigation:** pass only an opaque patient FHIR ID; each destination must independently authenticate and authorize that patient.
- **FHIR transactions and duplicate prevention:** email preflight can prevent common duplicates, but it is not atomic. Registration and invitation are separate requests; handle partial success. Do not claim race-proof uniqueness without a supported server constraint.
